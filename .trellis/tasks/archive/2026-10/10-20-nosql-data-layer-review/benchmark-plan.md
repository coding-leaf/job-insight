## 1. 要验证的假设

| 假设 | 支持它需要什么 | 什么结果会推翻或削弱它 |
| --- | --- | --- |
| H1 文档模型降低详情/证据重组成本 | 同 DTO 下，可审查的实际转换路径更少且更易维护 | MySQL JSON 也一次返回同一对象，维护复杂度相近 |
| H2 技能数组查询适配 MongoDB | 正确语义、多键索引及实际扫描/传输指标合理 | SQL 合理索引更优，或 MongoDB 仍大范围扫描 |
| H3 聚合管道减少应用工作量 | 同样输出下，往返、应用内存或传输量有实测减少 | 大量中点仍传回 Python，或 SQL 相同/更优 |
| H4 版本发布能保护数据替换 | 中断、重试、冲突和回退都保持可解释状态 | 部分版本可见、重复计数、指针与可读数据不符 |
| H5 原始结构灵活值得采用 | 有真实不同来源/结构输入和经验证的映射/保留成本 | 只有当前一个固定结构，或 SQL JSON 成本相近 |

H4 是通用架构能力，不能作为 MongoDB 独有优势。H5 缺实际输入时标为未验证，不用旧脚本推定。允许结论为无显著优势或对照更好。

## 2. 实验环境与隔离

- 候选 A：MongoDB Community 7.0，单实例；具体补丁、镜像摘要、驱动、配置记录。
- 对照 B：MySQL 8.4 InnoDB，关系模型。
- 对照 C：同版本 MySQL，类型列 + JSON 模型；记录是否配置生成列/多值索引及限制。
- 三者使用同机器、同 CPU/内存/磁盘限制，按顺序交错运行，避免同时争资源。
- 异步服务对照应采用可比执行方式；不能用一个同步阻塞客户端与另一个异步客户端的吞吐差直接说明数据库优劣。
- 使用专用数据库命名空间，例如 job_insight_eval_<run_id>。禁止连接/写入 job_insight、旧 jobs 或删除现有卷。
- 自动 JSON 回退必须关闭，连接失败即实验失败；日志记录实际服务器版本和数据版本。
- 不要求新搜索/图数据库部署，也不要求副本集、分片或云服务。

可记录容器命令，但本轮不运行；任何后续清理只针对经过绝对路径/数据库名核实的实验空间，不能使用泛化清库命令。

## 3. 输入、正确性参考与溯源

### 3.1 主测试集

使用 research/input-audit.json 指定的真实投影，导入前核对 SHA-256。输入不在 Git 中，缺失时先报告并请求已批准材料，禁止重跑旧脚本补齐。

对照三种模型必须：
- 包含相同代表 ID、全部来源成员、技能/依据、标量值、null 和工资排除标记。
- 不把重复来源 ID 当新增岗位；不在某个数据库提前删无标签/薪资缺失岗位。
- 不把 JSON 输出当作原始 19 列分组证据；只有源文件到位才核验原始分组，否则只验证同一投影集合。

### 3.2 独立正确性参考

新写的短小只读参考逻辑直接读取输入，按需求定义计算结果，不调用任一数据库仓库实现，也不复用废弃脚本：
- 列表按条件筛选、排序同值 id 升序后分页。
- 薪资资格沿用已有标志与约定；工资区间重叠包含端点。
- 中位数与 P25/P75 使用当前 exact inclusive 口径；先比较未格式化值，再核对 API 四舍五入。
- 技能 K(s) 同组只计一次；N 是筛选后全部组，L 是有标签组；零分母为 null。

这段参考代码只能证明投影上的查询一致，不能证明原网页薪资真实、岗位仍在招或原分类正确。

### 3.3 故障与扩容数据

故障边界可以用明确标记的测试夹具（缺字段、重复 ID、部分导入等），只进入隔离实验，不进入产品页面。

若缺两份真实内容版本，版本变化测试只能称为合成故障/机制测试，不能称为真实招聘变化历史。规模扩展若使用复制/生成输入，单列为合成压力测试，不用于市场结论，不用于宣称已有百万招聘数据。基础评估不要求扩容。

## 4. 固定工作负载

先从真实输入确定测试 ID、存在的来源别名及筛选条件，保存选择规则与固定随机种子。覆盖高/中/低选择率，不挑选某个数据库唯一擅长的条件。

| 编号 | 同等任务 | 正确性/实现注意事项 |
| --- | --- | --- |
| Q1 | 按代表 ID 和来源成员 ID 取完整详情 | 相同 JobItem；Mongo 一次查询不等于 SQL 必须 N+1；SQL JSON 允许整体返回 |
| Q2 | 类别+省份+学历精确标签+工资区间的 count 和分页 | 同样的区间资格、边界及稳定排序；不把学历标签改为个人可申请范围 |
| Q3 | 指定技能 all/any，与公共条件组合 | 数据库层实验；空列表省略筛选；不得用关键词 regex 替代严格标签查询 |
| Q4 | 当前范围总量、技能覆盖、Top K 和双分母 | 展开技能后不放大 N/L；零组与零标签组区别明确 |
| Q5 | 同范围类别/省份 exact 工资中位数及四分位数 | 两侧采用相同精度；若共用 Python 计算，分别报告 DB 与应用成本，禁止一侧近似另一侧精确 |
| Q6 | 全量导入同一输入两次，以及失败后重试 | 同输入契约版本幂等；无新增重复组、不覆盖已发布版本、不丢依据 |
| Q7 | 在 staging 导入中断、两发布者竞争、回退 | active 旧数据仍可读；CAS 冲突可见；完成指针切换后请求读取确定版本 |
| Q8 | 数据库不可用、在线岗位不存在 | 不回退旧 JSON、不谎报零组或成功；404 与连接故障区分 |
| Q9 | 发布附近的并发读取及多 API 请求 | 每次请求记录版本；不把请求内一致误写为跨请求绝对一致 |

Q6–Q9 可以先用最小实验服务验证，未获生产改造许可时不得直接改应用路由。H5 只在另行提供真实异构输入后追加，不作为当前必过项。

## 5. 性能、成本与公平性

正确性先于性能：结果集合/计数/空值/依据不等义时停止排名。

建议起点：每条读查询预热 20 次，正式计时 200 次，至少 3 轮；并发 1 和 4 分别记录。若结果受环境噪声主导，增加重复或报告无法区分，不从单次快慢下结论。

记录：
- 端到端 p50/p95、原始样本、错误率；数据库执行时间另列。
- 数据库/应用 CPU 与内存、实际返回字节、网络往返次数。
- Mongo explain 的 keys/docs examined、排序等；MySQL EXPLAIN/ANALYZE 对应实际指标，禁止硬凑字段一一相同。
- 数据大小、索引大小、导入时间；索引额外写入成本。
- 参数、查询文本、驱动版本、缓存状态、运行顺序、机器/容器资源限制。

每种模型都允许合理调优；调优预算和改动记录一致，不故意让 SQL 无索引。冷缓存只能在可复现条件下单列，不能把一侧预热另一侧未预热混测。

开发成本记录模型映射、校验规则、DTO 重组、索引维护、测试和版本迁移步骤。代码行数/表数只作线索，不直接变成“复杂度分数”；实际工时若未记录，就不事后编造。

MongoDB 的查询规划随数据分布变化；当前 2251 组的小样本结果只适用于该负载。即使出现性能优势，也说明它属于哪类查询，不泛化为整个系统或所有 NoSQL。

## 7. 决策门槛

1. 正确性不过，不给性能胜负结论。
2. 计时差异未超出重复运行的噪声，不声称明显优势。
3. 当前真实数据没有异构/历史，不给对应能力的业务收益评分。
4. 关系模型或 JSON 对照更简单时，保留这个结论；在 NoSQL 约束下说明采用 MongoDB 所付出的实际代价。
5. 若生产候选引入超过收益的版本管理复杂度，可选择更小的数据层方案，不强制部署所有候选集合。
6. 任何正式迁移另经用户审阅，实验报告不自动授权生产改动。
