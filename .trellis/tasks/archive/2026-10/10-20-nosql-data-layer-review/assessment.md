# NoSQL 复评结论：招聘主题与应用功能保留

> 2026-10-20 归档说明：本次研究已结束，没有获批的实施或验证交接；文中后续候选保留为历史材料，参见 closure.md。

## 1. 当前结论

**MongoDB 是可验证的文档型候选；目前不能声称它比 MySQL 更快、更省成本或不可替代。**

当前正式数据单来源、固定字段、单快照且规模较小。这一负载与关系模型也相容。仅凭“招聘数据”“有 JSON”“能收藏”不足以证明 NoSQL 的明显优势。

NoSQL 是用户已确认的项目约束。评估目标是在约束内选择合适的数据模型，并用真实结果陈述适配收益与代价；不需要制造 MySQL 无法实现的功能，也不允许把“必须用 NoSQL”本身写成性能结论。

## 2. 应用层与数据层分开

现有工作台、岗位探索、收藏、对比、技能核对和图表保留。它们产生详情、分页筛选和统计等负载，数据库负责组织和执行这些负载。数据库选型并不要求更改应用功能。

用户收藏仍按现有浏览器实现运行。本轮撤回“为了体现 MongoDB 价值，必须迁移个人工作空间”的默认方案；除非后续独立批准，它不属于本轮数据层改造。

## 3. MongoDB 值得验证的适配点

| 适配点 | 具体负载 | 当前证据 | 可接受的结论边界 |
| --- | --- | --- | --- |
| 岗位作为聚合文档 | 一次读取岗位字段、技能与各自来源依据 | 现有 JobItem 已是这种结构 | 可比较对象重组复杂度；不能声称关系库必须大量 JOIN |
| 有限嵌套数组 | 按技能名组合筛选，保留同一技能下完整依据对 | 已有技能数组和部分索引 | 数组查询/索引是实际能力；MySQL JSON 和关系表也可实现 |
| 聚合管道 | 同范围的组数、技能频次和薪资样本处理 | 现有 Mongo pipeline 已存在 | 可比较数据库工作量、往返次数和传输数据；不能假定更快 |
| 文档完整性边界 | 替换一个岗位资料时同步技能及依据 | 字段属于同一岗位聚合对象 | 单文档更新可原子完成；跨集合操作仍需专门设计 |
| 数据版本发布（候选） | 通过校验的数据集整体上线，失败保持旧版本 | 当前有离线处理产物，没有版本发布服务 | 可验证改造方案；不伪装成现有历史数据能力 |

以上能力说明参见 research/sources.md 的 M1–M7。表中的“可能减少复杂度”属于本项目推断，验证前不算收益。

多来源原始文档保留、字段演化和长期变更追溯确实适合进入候选评估，但本轮不把它们当作已获批准的新业务。旧脚本弃用，不能利用其实现细节绕过这个边界。

## 4. 公平的 MySQL 对照

需要同时考察两条路径：

1. **关系模型**：岗位公共字段一表，来源成员和技能关系分别建表；技能依据可按关系继续存储或在单条技能关系中存 JSON。详情通过聚合/批量读取恢复同一 JobItem，使用主外键与唯一约束维护一致性。
2. **混合 JSON 模型**：常用筛选字段使用类型列，完整岗位聚合体存 JSON，利用 JSON 函数/JSON_TABLE 处理嵌套关系，按实际版本限制配置表达式、生成列或多值索引。

MySQL 本身支持 JSON 及 JSON 数组索引（S1、S2）。因此“Mongo 一次读取对象”对比“SQL 必须十次请求”不是有效实验。若 MySQL JSON 同样一次返回完整对象，应该如实记录两者接近。

关系模型的约束和事务是优势；MongoDB 在文档边界内的整体读写和对象形状也有便利。应测量哪一种在本项目实际更省代码、数据转换与维护成本，而不靠表数或代码行数单独下结论。

## 5. 其他 NoSQL 类别的适配性

| 类别 | 需要什么负载才值得考虑 | 当前判定 |
| --- | --- | --- |
| 图数据库 | 真实多跳关系、变长路径、先修技能/课程等可验证边 | 当前只有少量技能标签与岗位关系，没有充分图遍历需求；暂不选 |
| 搜索引擎 | 排名质量、文本高亮、检索相关性成为核心目标并具备评测集 | 目前是结构化筛选与样本分析；不新增第二套服务，不能以“中文搜索”一词直接胜出 |
| 键值/缓存型 | 实时计数、限时状态或高频热点等已测需求 | 当前没有证据需要；不为满足 NoSQL 而加缓存 |
| 宽列/分布式写入型 | 持续高写入与明确分区访问模式 | 当前体量和采集事实不足，不引入分布式基础设施 |

这是按现有负载作的排除判断，不是对各数据库产品能力的完整排名。

## 6. 数据层候选方案及必要性

优先验证两件事，保持应用 API 不变：

- **文档聚合与索引**：岗位基本字段、有限技能/来源依据放在一个岗位组文档中，读取和筛选由数据库执行，列表与统计使用相同组集合。
- **可恢复的数据替换**：若要用新数据替换现有样本，先在隔离版本中完成校验，发布后读取明确版本，失败仍能读取旧数据。

后者解决的是新数据不能半导入、不能悄悄混合新旧资料的问题，MySQL 也可以做。它属于数据层可靠性设计，不是 MongoDB 的专属卖点。design.md 给出可验证候选，尚未要求生产实施。

JSON 保留为只读输入/测试证据；是否保留显式离线模式由生产改造审阅决定。比较数据库时必须禁用自动 JSON 回退，否则实验可能测到内存实现。单个线上详情缺失时也不能混入本地旧记录。

## 7. 优势成立与不成立的条件

**可以声称的条件性收益**：
- 同等 DTO 与查询语义下，文档模型减少了实际对象重组/迁移工作，且有可审查实现和验证记录。
- 相同输入和资源下，某些操作的执行计划、传输量或延迟确有改善，明确指出是哪一种查询、哪个索引和数据范围。
- 新资料字段变化时，原始证据不丢失，兼容路径受控且不用重写历史资料；需实际输入证明。

**不得声称**：
- 数据量小就一定快、NoSQL 天生比关系库适合“大数据”、有索引就所有查询命中。
- schema 灵活等于不用定义类型，或没有标签可以由系统猜出技能。
- 2,251 组可以代表百万级吞吐；复制扩容的数据能证明真实市场规模。
- 拥有文档版本模式就自动获得历史、实时订阅或多文档原子性。

若对照结果相近，结论应是“在本负载上性能收益不显著，选择主要依据文档组织及既有实现复用”；若 MySQL 更简单/更快，记录它并收窄 MongoDB 的优势陈述。NoSQL 约束不会改变实测结果。

## 8. 下一步与当前限制

下一步应是经批准的隔离对照验证，而非直接迁移生产、改页面或编写新爬虫。benchmark-plan.md 已规定查询、指标和故障用例；implement.md 规定接手门槛。

本次只完成资料与代码研究、输入审计和候选设计。没有启动 MongoDB/MySQL、运行性能测试或产生“胜出”数据。缺乏真实多版本/新来源输入时，相应结论保持未验证。
