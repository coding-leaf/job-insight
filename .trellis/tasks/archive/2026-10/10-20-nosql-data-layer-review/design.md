# 数据层候选设计与兼容边界

> 已归档关闭：以下是未获实施批准的历史候选，不作为新改造方案交接，详见 closure.md。

状态：用于比较和验证的方案，不是实施批准。应用功能、用户收藏和对比行为保留。现有业务脚本全部不作为依赖。

## 1. 分层与访问契约

~~~text
经明确验收的数据输入（当前只读投影文件）
        ↓ 新的、受校验的导入边界（尚未实现）
隔离数据版本 → 校验 → 明确发布
        ↓
数据库查询仓库 → 既有 FastAPI DTO/API → 现有前端
~~~

保持：
- 既有 /api/v1/jobs、/jobs/{id}、/overview、/meta/options 和 stats 路径及包装体。
- JobItem 字段、技能/依据关系、source_ids 和代表 ID 的业务含义。
- 组级筛选先于分页与统计；薪资资格、区间重叠、分位数口径及技能双分母。
- 岗位详情与比较使用岗位原文和实际缺失值，不承担“当前在招”或个人适配预测。
- 前端个人状态仍由既有 workspace store 负责，不引入服务器用户集合或登录。

允许在后续获批实现中改内部仓库、数据库配置及非可见的数据读取协调，不要求重做页面。批量多技能查询首先只是实验负载，不能默认为已批准的新 API 参数。

## 2. MongoDB 候选：聚合文档

### 2.1 最小岗位存储

每个岗位组保持一个文档，公共字段采用已有 JobItem 形状。skills 是有限且按技能名去重的数组，每项 provenance 保留不同来源/依据对；source_ids 保留全组来源成员。

详情可一次返回完整聚合对象，不把不同技能和不同依据拆开后任意拼配。内部 _id、release_id 等存储元信息不泄露为替代业务 ID；响应仍通过现有 DTO 投影。

新业务资料按同一文档完整替换时，使用明确条件更新或写入新的不可变发布版本。单文档原子性不会自动覆盖多个文档或整个数据集（M4）。

### 2.2 原始证据与结构演变的可选层

若后续明确需要保留异构来源或历史原始资料，可以增加 source_snapshots：
- source、source_record_id、content_hash、schema_version、原始 payload、已确认的来源 URL 和采集/提供时间。
- 按来源、稳定来源 ID、内容哈希建立幂等身份；相同内容的重复观测与“内容发生变化”分开。
- 旧数据缺少采集时间时保留未知，不把 published_at 或导入时间伪装为采集时间。
- 原始证据与规范业务投影分离；source_id 的稳定身份和 19 列精确分组的展示 ID 不是一回事。
- 版本历史单独存文档，不向一个岗位文档无限追加 history 数组。

该层当前不是必做迁移：只有实际输入和追溯需求到位才落地。已有分组投影无法凭空还原所有原始 21 列成员记录；缺原始文件时，不能声明已验证完整组级追溯。

## 3. 可验证的数据发布候选

解决批量写入中途失败、新旧版本混合和可回退问题，不更换招聘主题或用户功能。是否正式采用需看验证与维护成本；不把这个模式包装成 MongoDB 独有。

### 3.1 三个核心集合

| 集合 | 内容 |
| --- | --- |
| data_releases | release_id、输入摘要、投影契约版本、预期/已验证组数、校验结果、staging/ready/failed 状态 |
| job_groups | release_id + 完整既有岗位组对象；唯一身份由 release_id 与业务 id 共同确定 |
| dataset_registry | 固定 _id=active，active_release_id、revision、published_at |

当前 jobs 继续作为旧实现的数据源，候选只在独立实验数据库创建，禁止直接覆盖或重命名。生产迁移时的集合名和切换由后续审阅决定。

### 3.2 导入契约

输入至少包含：
- 可读取的实际数据文件、字节级 SHA-256、projection_contract_version。
- 来源范围、数据局限、已知统计排除规则及对应验证依据。
- JobItem 集合，以及保留原始分组的必要证明；缺少证明时如实标为仅验证既有投影。

release_id 由输入字节摘要与投影契约版本确定。相同输入/版本重复执行应收敛到同一版本；文件字节变化可产生不同版本，不把它等同于市场内容必然变化。

导入前验证：类型、业务 ID 唯一、source_ids 非空/唯一/包含代表 ID、代表为字典序最小、来源成员不跨组重复、技能名唯一、依据对不串配、工资资格与排除标记、所有有限数值合法。不能只用 Pydantic 默认值掩盖缺字段，也不能重新按归一化结果擅自合组。

未知投影契约版本显式拒绝；保留原始来源资料与旧版本，不自动猜字段映射或调用废弃处理脚本。

### 3.3 阶段写入与发布

1. 创建/识别 staging 版本，只向该版本写入。
2. 重复批次只核对同一份输入；若同 release_id 下内容不一致，停止并报告。不要 replace 已发布数据。
3. 校验预期文档集合、成员唯一性、组级统计与输入摘要；达到条件后将版本标记 ready。ready 数据不可继续原地修改。
4. 读取 active 指针及 revision。
5. 以预期 revision 为条件，单次原子更新 registry，指向已 ready 的候选并递增 revision。
6. 条件不匹配说明其他发布者已先完成，返回冲突；不静默覆盖。

发布前崩溃只留下 staging，旧指针继续服务；发布后无需再跨集合修改 active 标记，活动状态由 registry 唯一解释。不得把“多次 insert 成功”当作整个数据集原子发布。

回退是把 registry 用同样的预期 revision 机制指向已验证的旧 ready 版本，递增 revision。旧版本不会被默认删除；清理须保证不删除 active 或仍需读取的版本，并另行授权。

使用的是应用层 staging + 单文档指针，不默认依赖多文档事务、副本集、Change Streams 或队列。

## 4. 查询、索引与一致性

### 4.1 版本边界

每个 HTTP 请求开始时解析一次 active_release_id，随后本次请求内所有详情/计数/聚合都固定使用该 release_id。

生产候选可以在响应头 X-Data-Release 记录版本，用于追溯。跨多个 HTTP 请求若正好遇到发布，不自动保证同一版本；要实现前端多请求批次一致，需要客户端显式固定版本并由后端校验该版本仍可读。此协调属于后续兼容审阅，不能因为各请求都取 active 就声称绝无混用。

尤其现有薪资页并发请求类别与省份统计，实验必须观察各自版本。不得把本设计的“请求内一致”写成“所有页面始终同一快照”。

### 4.2 候选索引（待 explain 选择）

最小身份约束：
- unique(release_id, id)。
- unique(release_id, source_ids) 的多键约束，用于来源成员不能跨岗位组重复；输入校验另保证单个数组内无重复。

候选工作负载索引，不要求全部建立：
- (release_id, job_category, province, id)。
- (release_id, salary_eligible_for_midpoint, job_category, salary_midpoint, id)。
- (release_id, skills.skill_name, id)。

source_ids 与 skills 是独立数组，不把二者组合成同一个复合多键索引。工资上下限重叠、不同排序方向、关键词 regex 并不会因这些定义就自动高效；逐个 explain，记录排序/扫描/索引代价。

不同排序值相同时以 id 升序稳定返回，不沿用当前缺少明确同值规则的行为作为正确性基线。

### 4.3 技能与证据条件

- 查询“同时包含若干标签”可以使用 skills.skill_name 上的 $all；空条件应省略而非传空 all。
- 条件必须属于同一个技能/依据元素时，用相应层级的 $elemMatch，避免分别命中两个元素却误认为同一证据。
- 默认技能频次同组一次；实验保留输入去重约束，若故意注入重复标签做边界测试，必须拒绝或在聚合先按组/技能唯一化。
- 详细依据不能被当作正文引文；当前 source_tag 仅是来源标签。

## 5. 等义 MySQL 对照设计

### A. 关系模型

job_groups 存公共标量字段及 release_id，键为 (release_id,id)；group_sources 存成员；group_skills 存唯一的岗位/技能关系，provenance 可用结构化关系或 JSON。按查询需要创建同样合理的复合索引、唯一约束和外键。

详情允许通过一个聚合 SQL 或固定批量请求组装，不能强迫 N+1。技能查询要匹配同组集合；展开关系后组数/薪资不重复。别名来源 ID 也必须可查。

### B. JSON/关系混合模型

常查公共字段用类型列，完整 DTO 用 JSON 存储；通过 JSON_TABLE 或相应 JSON 函数访问 skills 与 provenance。需要数组索引时按 MySQL 8.4 的实际限制选多值/生成列方案，先证明语法和计划有效，不能假设与 MongoDB 索引一一对应。

如果增加派生 skill_names，必须由同一导入边界维护与 payload 一致，不允许双份不同义数据。将该维护代码和索引存储都算入成本。

两种 SQL 模型都可采用 ready 数据版本 + active 指针；SQL 事务也可用于其合理边界。比较同等正确性，不强迫 SQL 模仿 MongoDB 的每一条内部操作。

## 6. 运行模式与迁移建议

实验必须使用真实 MongoDB / MySQL 连接，禁止 JSON 回退。生产候选可设计显式 DATA_BACKEND=mongodb|json，默认 mongodb，json 仅经明确选择才启用；这一配置尚未实施或批准。

选 mongodb 后连接失败应拒绝就绪或明确返回不可用；MongoDB 查不到岗位应保留未找到状态，不从本地旧数据补齐。json 模式不能宣称数据库验收通过。

迁移候选顺序：隔离验证 → 非破坏性建立新集合/索引 → 校验同 DTO 与同统计 → 审阅批准 → 明确切换 → 保留旧数据回退。不要运行旧 seed.py、清空 jobs 或删除卷。

现有 Motor 在官方生命周期内已进入弃用阶段，评估新代码时优先核实 PyMongo Async 的兼容性；不在本轮改驱动，也不要将换驱动的性能差异计为 NoSQL 优势。

## 7. 兼容性与未知项

旧数据在本机存在但 Git 忽略；克隆后找不到时，等待用户提供同一已批准输入或接受新的明确输入，禁止伪造基准。

来源原始资料不足、真实版本不足和实际数据库性能未测，分别保留未知；它们不阻塞本轮文档交付，但限制最终优势结论。若验证显示版本发布服务过重，可只保留可核对的导入摘要/版本标识，不强制部署完整候选。

任何需要新增 API 参数、迁移浏览器个人状态、新建采集能力或改变原始 19 列规则的发现，先回到规划审阅，不由实现者自行扩大。
