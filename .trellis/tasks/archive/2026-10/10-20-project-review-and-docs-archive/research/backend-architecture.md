Reviewed on 2026-10-20. This is research for a documentation task, not authorization to change application behavior.

## Current implementation

- `backend/app/main.py:29` manages database connection in the FastAPI lifespan; `/health` only reports application status, not a verified active data source.
- `backend/app/core/config.py:6` uses Pydantic Settings and environment files. `docker-compose.yml:3` declares one MongoDB 7.0 service, a port and a named volume; it does not deploy the complete frontend/backend system or declare a replica set/sharding.
- `backend/app/api/v1/api.py:10` mounts metadata, overview, statistics and jobs endpoints. There are seven business GET paths (options, overview, category salaries, region salaries, skill top, job list, job detail), plus `/health` and generated API documentation.
- `backend/app/api/v1/endpoints/stats.py:18` and `overview.py:16` forward category, province and education only. The jobs list additionally accepts keyword, salary interval and skill-presence conditions. Do not claim all list-specific conditions automatically filter every chart.
- `backend/app/schemas/response.py` supplies the `{code,message,data}` envelope. `frontend/src/api/client.ts:15` sets the `/api/v1` base and validates response codes; individual endpoint functions obtain the nested data.
- `backend/app/db/mongodb.py:15` pings MongoDB and sets `db=None` if initial connection fails. This is startup fallback, not a demonstrated transparent failover after an established connection fails.
- `backend/app/db/repository.py:160` always loads a local JSON dataset and ID lookup during repository construction, including when MongoDB will later connect. Database mode therefore does not eliminate the application's local dataset memory cost.
- `repository.py:294` uses `$facet` for overview counts, categories and salary midpoint extraction. `:375` and `:438` group salary arrays by category/region. The final exact median and quartiles are calculated by Python `statistics` (`:91`), rather than entirely inside MongoDB.
- `repository.py:501` uses `$facet`, `$unwind` and `$group` for skill frequency and both denominators; current group-level arrays are produced upstream with unique skill names. This is native aggregation, not merely storing JSON in MongoDB.
- `repository.py:585` runs `count_documents` and `find().sort().skip().limit()` for the list; `:615` searches representative/member source IDs for details.
- `repository.py:955` falls back to `_id_index` even if a connected MongoDB returns no detail document. A returned detail therefore does not always prove that record exists in the active Mongo collection.
- The Mongo list sorts on one requested field (`:601`); the statistical contract's explicit ID tie-breaker is not visibly added. Record as a contract difference, not an approved code fix.

## Selection assessment boundaries

MongoDB is actually used in the implementation for document reads, filtering, pagination and native aggregation. The job document shape conveniently holds fields, source IDs, skills and provenance together. Those are real uses.

The current small, fixed-schema, single-source, read-oriented snapshot does not demonstrate a requirement for MongoDB specifically. Existing JSON/Python mode already implements the exposed reads. This proves a functional alternative for the current snapshot, not identical concurrent performance or production suitability. A relational model (or a mixed relational/JSON model) can represent the same information. Database replacement remains outside this task.

Earlier archived review PRD records a NoSQL project constraint; its `closure.md` explicitly says no MongoDB performance superiority was established and no proposed redesign was approved. Reuse that decision boundary. Do not invent server-side favorites, versions or extra services simply to strengthen a database narrative.

An appropriate explanation is: the database has real responsibilities, but its unique technical necessity has not been established for the present requirements. If NoSQL remains an educational/project constraint, describe it honestly as a constraint and explain the document/aggregation implementation. Without that constraint, simpler storage is a reasonable candidate to assess; do not claim measured superiority for any untested alternative.
