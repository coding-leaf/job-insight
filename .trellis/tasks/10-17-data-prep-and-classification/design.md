# 数据清洗规范与双路岗位分类实施 — 技术设计方案

## 1. 架构与边界设计 (Architecture & Boundaries)

本任务定位为离线可复现的数据处理流水线及核验工具集，严格遵循数据字典与分类契约。

### 目录与模块划分

```text
scripts/data_prep/
├── __init__.py
├── clean_and_group.py      # 原始19列精确分组、代表ID确定、技能聚合、数值安全转换与省级规范映射
├── rule_classifier.py      # 规则分类引擎：基于标题优先、专业限定词、正文辅助的确定性分类
├── ai_classifier.py        # 独立 AI 分类引擎：隔离规则输出，仅基于标题、正文与类别说明生成提案
├── category_adjudicator.py # 双路比对、单来源状态机与组级一致性裁定，导出 9 列 review CSV
├── sampling_audit.py       # 抽样审计生成器：分类重点复核清单与抽样、技能真实性抽样、305组重复语义抽样
├── pipeline.py             # 一键式完整运行流水线
└── verify_contracts.py     # 验收测试：8项验收标准自动化断言、原始哈希复测

data/processed/             # 产物输出目录（不修改外部输入文件）
├── jobs_cleaned_grouped.json   # 2251 个岗位组的完整结构化业务对象
├── job_category_review.csv     # 3000 条来源记录的标准 UTF-8 BOM 离线复核快照（9 列）
└── audit_reports/
    ├── classification_review.md # 冲突/多岗位/校招清单与抽样结果
    ├── skill_accuracy_audit.md  # 技能标签真实性抽样核对报告
    └── duplicate_groups_audit.md# 305组重复记录业务含义分析报告
```

### 外部边界约束
- **输入源绝对只读**：`../清洗后数据/` 路径下的 `jobs_clean_final.csv`、`skills.csv`、`job_skills.csv` 仅供只读流式或批量读取。
- **输出隔离**：所有衍生中间文件与目标文件均输出到当前工程的 `data/processed/` 目录下，禁止覆写原始文件。

## 2. 数据流与核心契约 (Data Flow & Contracts)

### 阶段一：原始 19 列分组与清洗
1. 读取 `jobs_clean_final.csv`（处理 UTF-8 BOM），提取除 `id` 和 `source_url` 外的 19 列原始文本元组。
2. 保持未 trim、未转数值、未映射地区的原始字符串，构造精确字典键。
3. 统计各组，确定最小字典序 ID 作为代表 ID，组内所有 ID 按升序排列记录为 `source_ids`。校验总组数为 2251 组，多记录组为 305 组。
4. 关联 `job_skills.csv`，将同一组内所有成员关联的技能并集聚合，按 `skill_name` 归并，同时保留各自的 `(origin, evidence)` 元组列表。
5. 针对各组执行非破坏性清洗：
   - 空值转 `null`，技能为空转 `[]`。
   - `recruitment_headcount` 和 `experience_min_years` 解析：遇到如 `"5.0"` 安全转为 `5`。
   - 省级映射：四省规范映射（“广西省”->“广西壮族自治区”、“内蒙古省”->“内蒙古自治区”、“新疆省”->“新疆维吾尔自治区”、“西藏省”->“西藏自治区”）；城市缺失保持 `null`。
   - 薪资校验：标记有效闭区间、缺少上限（不计中点）、3 条已知原文倒置排除（`Am6VEAbf4rZZ4mwyaKuHBe`, `DBvsD7jVecfg3YmmnLaSHo`, `gmFNdf4Ef3TeSbWzfEeon`）。

### 阶段二：双路岗位分类
1. **规则分类引擎 (`rule_classifier.py`)**：
   - 严格落实 11 类别白名单。
   - 模式匹配体系：
     - 优先排查“标题包含多岗位/斜杠”（如 `Java开发/软件测试`）以及“无明确职责校招”（如仅含 `2027届校园招聘`、`管培生`、`实习生` 无正文或仅泛泛宣讲），直接置空，原因记录为多岗位或信息不足。
     - 专业限定词前置：例如 `数字前端` -> 硬件与芯片；`Web前端` -> 软件开发；`算法工程师` -> 算法与人工智能。
     - 标题与正文交叉验证：若标题与正文主体职责发生实质矛盾（如标题“产品经理”正文“电路设计”），置空并记录冲突原因。
2. **独立 AI 分类引擎 (`ai_classifier.py`)**：
   - 隔离规则通道输出，作为第二路独立审读器。
   - 输入仅为各岗位 `title`、`major_requirement`、`description` 和 11 类别定义。
   - 输出 `job_category_review`、`review_source="AI:Opencode"`、`review_reason`、`review_status="pending"`。
   - 遇到信息不足、校招综合或多岗位并列时，独立判定为 `null` 并写明理由。

### 阶段三：裁定与组级合并 (`category_adjudicator.py`)
1. **单来源结果推导**：
   - 无提案且 pending：取规则。
   - 有提案且 pending：与规则一致取规则；分歧（含一方为空）两者置空（代表存在未决分歧）。
   - 有提案且 confirmed：取提案结果。
2. **组级类别推导**：
   - 遍历组内所有成员。若存在任何一个成员处于未解决分歧（pending 冲突），组级两字段均置空。
   - 收集组内有效决定（非空规则或 confirmed 决定）；若有效决定之间存在冲突，组级置空等待人工裁定。
   - 若全部有效决定一致，采纳该类别。
3. **输出**：生成 3000 行的 UTF-8 BOM `job_category_review.csv`。

### 阶段四：三大抽样审计报告 (`sampling_audit.py`)
1. **分类重点复核清单与一致项抽样**：
   - 完整列出两路分歧项、多岗位项、笼统校招项、标题正文矛盾项。
   - 对两路一致项按各类别分层随机抽样（每类别至少抽查 5-10 条），输出核验评估。
2. **技能标签真实性抽样质检**：
   - 针对 1107 个有标签岗位，按类别分层抽样 50-100 个岗位。
   - 对照岗位 `description`，核查标签技能是否在正文中出现或有明确对应要求，分析“依据仅重复技能名”的客观质量、噪声率与业务局限。
3. **305 组重复记录业务含义抽样**：
   - 抽取 30-50 组具有多记录的岗位组，横向对比其 `published_at`、`source_url`、公司、薪资等。
   - 分析是由于重复抓取、定时刷新重发，还是不同批次招聘，明确为何当前精确去重无法替代独立招聘岗位识别。

## 3. 错误处理与边缘用例矩阵 (Validation & Edge Cases)

| 场景 / 边界用例 | 系统预期行为 |
| --- | --- |
| 原始 19 列相同，但 ID 与技能关联不同 | 聚合为一个岗位组，保留字典序最小 ID，合并技能并集及不同来源依据对。 |
| 浮点数字符串 `5.0` 作为人数或年限 | 转换为整型或浮点数值 `5`，不抛出异常。 |
| 包含 `广西省` 等别名 | 分组后统一转换为 `广西壮族自治区`，分组前仍基于原始文本。 |
| 原文倒置 3 条记录 | 组级别打上 `salary_stat_excluded=True` 标记，薪资计算中点时跳过。 |
| 规则给出“软件开发”，AI 给出“硬件与芯片” | 单来源与组级均判定为未分类，记录分歧，列入复核报告。 |
| 同一组内 A 记录与 B 记录分类提案不一致 | 组级类别置空，不允许由代表 ID 单方面决定整组类别。 |
| 仅含“2026校园招聘”且正文为空 | 规则与 AI 均置空，不可强行从公司或专业名称推测类别。 |
