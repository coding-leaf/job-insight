# 岗位分类与离线复核

本文件固定类别、判断依据与回填规则，供规则脚本、人工和现有 AI 编程工具共同使用。契约确定于 2026-10-17，状态复核于 2026-10-20：已有真实数据的离线规则分类和复核 CSV，但尚无人工确认完成的证据。分类只离线处理，当前未接模型 API，未建设在线复核页面。字段类型见[字段字典](data-dictionary.md)，本轮替换前的[原文快照](archive/2026-10-20_203614_job-classification.md)见[归档清单](review/2026-10-20_203614_documentation-audit.md)。

## 1. 固定类别与边界

每个岗位只采用一个主类别。以下 11 个标签必须原样使用；无法判断时用 `null`，页面可显示“未分类”。“其他明确岗位”要求职责已明确，不能用来收纳信息不足的记录。

| 类别 | 纳入依据与边界 |
| --- | --- |
| 算法与人工智能 | 算法研究、模型训练、机器学习、计算机视觉、自然语言处理等核心职责；仅调用现成 AI 接口的软件开发仍按主要开发职责分类。 |
| 数据分析与大数据 | 数据分析、数据仓库、ETL、大数据平台开发等；算法建模为主要职责时归算法与人工智能。 |
| 软件开发 | 网页前端、后端、移动端、应用软件及以软件编程为主的嵌入式开发；数字电路“前端设计”不属于本类。 |
| 软件测试 | 软件功能、自动化、性能测试及测试开发；硬件测试按硬件与芯片，不能只匹配“测试”。 |
| 运维与云平台 | 系统运维、SRE、DevOps、云平台运行管理；以客户安装、交付为主的实施归技术支持与实施。 |
| 网络与信息安全 | 网络工程、网络维护、信息安全、渗透测试等；通信协议与无线研发为主时归通信。 |
| 硬件与芯片 | 电路、电子硬件、芯片、数字前端、FPGA、芯片验证；“前端”需结合“数字、芯片、网页”等上下文。 |
| 通信 | 无线、射频、通信协议、通信系统研发与优化；一般 IT 网络部署归网络与信息安全。 |
| 技术支持与实施 | 面向客户的技术支持、部署实施、系统交付；不能因任意正文出现“支持”就命中。 |
| 项目与产品 | 明确的项目管理、技术项目经理、产品经理等职责；“工程师”不自动属于项目。 |
| 其他明确岗位 | 已明确职责但不属上述类别，如财务、销售、机械设计；必须写明实际职责依据。 |

标题优先、正文补充；专业名称、企业性质、公司名、技能标签不能独立决定类别。标题与正文核心职责明显冲突时进入复核，不以标题优先为理由忽略冲突。先识别专业限定词，再判断通用词；多个候选无法排除时规则结果为空，不按类别表的先后顺序强行命中。

| 构造示例 | 判断 |
| --- | --- |
| `Java后端开发工程师`，职责为后端接口开发 | 软件开发，记录标题或对应职责依据。 |
| `数字前端设计工程师`，职责为 RTL 设计 | 硬件与芯片；`Web前端工程师`归软件开发。 |
| `数据工程师`，无正文 | 不能仅靠“数据”确认分析、平台或算法职责，规则留空，等待复核。 |
| `测试工程师`，正文明确芯片验证 | 硬件与芯片。 |
| `某公司2027届校园招聘`，无具体职责 | 未分类，不从企业或专业猜测。 |
| `Java开发/软件测试`，正文同时招聘两类且无主次 | 未分类并说明多岗位；本期不拆成多条岗位。若正文明确主要岗位且其余只是配合职责，可按主职责分类。 |
| `产品经理`，正文却明确负责电路设计 | 规则留空并说明标题/正文冲突，人工裁定后才能确认。 |

## 2. 独立提案与 CSV 格式

先冻结上述类别说明。规则通道依据标题/正文输出 `job_category_rule`、`rule_reason`；人工或 AI 通道只读取同一份来源标题/正文与类别说明，在独立给出判断后才对照规则结果。不得把规则结果当提示要求 AI 复述。人工可单独复核规则结果，但这种复核不能声称是独立提案。

复核文件采用 UTF-8 BOM CSV，每个来源 `id` 一条**当前快照**，列头固定如下；逗号、双引号及换行按标准 CSV 转义。类别空单元格表示 `null`，不能写字面量 `null` 或“未分类”。下列 `demo:` ID 仅为示例，实际文件必须引用主表的真实 ID。

```csv
id,job_category_rule,rule_reason,job_category_review,review_source,review_reason,review_status,job_category,category_source
demo:rule,软件开发,标题含Java后端开发,,,,pending,软件开发,rule
demo:agree,软件开发,标题含Java后端开发,软件开发,AI:Codex,标题明确后端接口开发,pending,软件开发,rule
demo:conflict,软件开发,旧规则仅匹配前端,硬件与芯片,AI:Claude Code,标题含数字前端且正文为RTL设计,pending,,
demo:confirmed,软件开发,旧规则仅匹配前端,硬件与芯片,人工:负责人,已核对RTL设计职责并验收分类,confirmed,硬件与芯片,reviewed
demo:unknown,,标题仅为校园招聘,,人工:负责人,已检查标题及缺失正文仍无法确定,confirmed,,reviewed
```

| 列 | 约束 |
| --- | --- |
| `id` | 必须存在于主表且在当前快照中唯一；不能按行号或标题回填。 |
| `job_category_rule`、`rule_reason` | 类别为固定标签或空；命中须给出依据，留空时可说明缺失、冲突或多岗位原因。 |
| `job_category_review` | 固定标签或空；空既可能表示尚无提案，也可能表示提案认为无法分类，由来源列区分。 |
| `review_source`、`review_reason` | 无提案时均为空；有提案时均必填。来源采用 `人工:姓名或角色` 或 `AI:工具名`。来源只标识提案由谁产生，不表示已确认。 |
| `review_status` | 仅 `pending`、`confirmed`。`confirmed` 表示人工/负责人已经验收当前提案，AI 不得自行设为确认。确认时必须有来源和依据；AI 提案被人工验收后可保留 AI 来源，在理由中记录验收人及验收依据。 |
| `job_category`、`category_source` | 按下一节重算的单来源结果；回填时校验，不允许人工随意填写一个与提案状态矛盾的结果。它们不是直接展示的组级结果。 |

独立性与确认是两件事：独立 AI/人工提案仍可为 `pending`；规则和提案相同也不自动变成 `confirmed`。一致项需抽样核验，冲突、无法分类及依据不明确项优先检查。人工裁定时允许修改提案，但须在理由中留下替代原因。

## 3. 单来源采用规则

比较类别时将空值视为 `null`；“无提案”仅指 `review_source` 和 `review_reason` 均为空。

| 当前状态 | `job_category` / `category_source` |
| --- | --- |
| 无提案，状态为 `pending` | 采用明确规则类别及 `rule`；规则为空则两者为空。 |
| 有提案，`pending`，与规则相同 | 规则非空时采用规则及 `rule`；两者为空时保持为空，不能称为已确认。 |
| 有提案，`pending`，与规则不同，包括其中一方为空 | 两者均为空，作为未解决冲突；不能继续采用规则类别掩盖分歧。 |
| 有提案，`confirmed` | 采用验收后的提案及 `reviewed`，覆盖该 ID 的旧规则判断；已确认无法分类时为 `null` / `reviewed`。 |

主表中没有复核行的 ID 等同于“规则为空、无提案、pending”，不丢弃岗位。非法标签、重复 ID、缺少来源/依据或状态组合无效须先修复，不能默认为已确认。

## 4. 重复岗位组的唯一分类

按[19 列精确键](statistical-methodology.md)成组后，对组内全部 ID 的当前记录统一计算，代表 ID 只负责展示，不替组裁定：

1. 只要任一成员存在上节的 `pending` 不一致提案，组级 `job_category`、`category_source` 都为空。其他 ID 的确认不能消除这个冲突。
2. 没有上述冲突时，收集各成员的有效决定：`confirmed` 提案（含确认的空类别），以及其余成员的非空规则类别。无提案、无规则等信息不足的空值不作为反对票。
3. 有效决定中类别不一致（含“确认无法分类”与明确类别并存）时，组级两字段均为空，等待组内裁定。不能多数投票或按代表 ID 取值。
4. 所有有效决定一致时采用该值；其中有已确认决定则来源为 `reviewed`，否则为 `rule`。没有任何有效决定时两字段均为空。

组内裁定须覆盖所有仍冲突的成员：在当前 CSV 中把受影响 ID 的提案改成同一验收结论，状态改为 `confirmed`，理由写明组内依据及被替代的旧 `pending`/确认判断。将裁定前快照另存留档后，再重算整组；不能仅确认代表 ID，也不能一边保留旧的冲突 pending 行一边宣称整组已解决。`confirmed` 只替代同一 ID 的旧判断。

例如同组 A、B：A 已确认“硬件与芯片”，B 仍有“软件开发”规则与“硬件与芯片”pending 提案，整组仍未分类；B 验收为“硬件与芯片”并明确替代旧判断后，整组采用“硬件与芯片”。若 B 已确认“软件开发”，也需复核并更新受影响成员，不能由 A 的较小 ID 决定结果。
